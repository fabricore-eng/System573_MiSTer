### THE OPEN BUG — music does not stop
Reported from play: songs keep playing after a stage is FAILED, and across small menu
changes. Leading hypothesis (the human's, and it fits every measurement): **the
enable-driven stop never actually fires, and music only ever ends when the song data runs
out** — i.e. the window-exhaustion backstop, not the real stop path.

Why earlier "this is fixed" conclusions were wrong — read this before re-deriving:
- I claimed the stop path worked because a 13-hour board log had **846,906** config
  adoptions reading `stream_en=0`. **That statistic never proved what I used it for.** It
  shows the firmware SEES stops; it says nothing about whether seeing one ever silenced
  anything, because if the drain was already off (song exhausted) such an adoption changes
  nothing and still counts.
- I also claimed the attract audio capture showed clean start/stop alternation. Comparing
  run LENGTHS instead: hardware plays for **15, 14.5, 47, 79, 14, 47, 47.5 s** continuously
  against MAME's ~23.5 s segments. Those long runs are consistent with music bleeding across
  boundaries until the window empties. The human correctly called duration-comparison an
  unreliable test — prefer the isolated causal check below.

**The fabric is NOT the problem** (checked statically): `rtl/s573_mp3_pcm.v:147-150` forces
`pcm_l/pcm_r` to zero when `drain_en` is low and gates `pcm_ce` so the read pointer cannot
advance. Clearing the drain genuinely silences the MP3 channel. So the fault is upstream:
either the firmware never clears `DRAIN_EN`, or something re-enables it.

**Instrumentation is already committed to settle it** (`6f8fe0a`): the two silencing causes
now print distinguishable lines —
`s573mp3: DRAIN OFF via ENABLES (...)` vs `s573mp3: DRAIN OFF via EXHAUSTION -- window done`.
They were indistinguishable before, which is exactly why ambiguous data produced a
confident wrong answer.

## Key decisions (and why)
- **Gain path is NOT the clipping fix.** MAME's curve is
  `gain_to_db(v) = round(20*log10((0x100000-v)/0x80000))`, `mult = v==0 ? 0 : 10^((db+6)/20)`.
  ddrsbm asks for `0xAF3CD` = −4 dB = **×1.2589, a BOOST**; unity is near `0xBFBDE`. Applying
  the game's gain faithfully makes us ~2 dB LOUDER. Do not "fix clipping" with it.
- **Clipping was retired as a non-bug** — 510 of 28,798,080 samples at the rails (0.0018%,
  longest run 0.15 ms). Peak-hold over a long capture answers "did any sample ever touch full
  scale", which was never the question.
- **The descramble scheme stays on the per-title OSD bit.** MAME does not auto-detect by
  CRCing the bitstream; it is a per-game config flag (`set_ddrsbm_fpga(true)`). Our OSD bit
  set by the `.mgl` already matches the reference.
- **Boot time is normal** (~4–5 min to attract vs MAME's ~4.3). An earlier "16 min, 3.5–4x
  slower" claim was retracted — it read a poll schedule label as a measurement.

# RESOLVED 2026-08-02 — the open bug above is a cfg_epoch width mismatch (firmware-only)

The capture this handoff asked for was run (de-confounded: warm reboot, uptime 23.8 s, ONE
load_core, bounded HB=1 SECS=1500 MAXMB=48, through attract AND a headlessly-failed stage).

**The decision rule did not fire the way it expected.**
```
DRAIN OFF via ENABLES    -> 18      # the rule was: zero => the enable path is dead
DRAIN OFF via EXHAUSTION -> 70533
```
Not zero. The enable-driven stop works. The leading hypothesis is REFUTED.

**Actual root cause** — `s573mp3_poll()` tests `r.cfg_epoch` (full 16-bit, on the hot PTRS
poll) but `apply_cfg` adopted `cfg.epoch`, and `CMD_573_MP3CFG` word0 carries only
`cfg_epoch[7:0]` BY DESIGN (`rtl/s573_hps_ext.v:335`, doc'd `:127`). Past 255 they can never
be equal, so the branch re-fires every poll, re-arming DRAIN_EN from a stale config and
resetting the decode counters. The game's stop is overwritten ms later, forever.

Proof from the heartbeats: 519 healthy (max epoch while equal 247); divergence begins at the
FIRST heartbeat past 255 (262); **229/229** diverged heartbeats satisfy `adopted == fabric %
256`, zero counterexamples.

**The fabric is correct as designed — no Quartus rebuild.** Fix is one line plus a loud
torn-read warning in the Main fork: `c->cfg_epoch = r.cfg_epoch;`
Committed as **3f52ed5** on branch `claude/system573-mp3-stop-bug-ifnn94` in `~/Main_MiSTer`
on dell (NOT pushed — that repo has no credential helper on dell).

**Verified on silicon** (fresh boot 16.9 s, one load_core, SECS=1800 to cross the boundary):
898/898 heartbeats `adopted == fabric` up to epoch 500, ZERO divergence; EXHAUSTION stops
70533 -> 9; ENABLES stops 18 -> 36; log 20.5 MB -> 234 KB.

**This retires the 846,906 stream_en=0 adoptions as evidence.** That number is this runaway's
signature — in the stuck state `apply_cfg` runs at poll rate indefinitely. Any statistic taken
from a long board log after the epoch passed 255 measured this bug, not its subject.

`debug=1` reverted from `MiSTer.ini`, capture scripts removed, devlock released.
Post-fix log kept at `de10:/media/fat/s573_capture_3f52ed5.log`.
